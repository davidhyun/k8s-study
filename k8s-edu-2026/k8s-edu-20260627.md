## 2. Storage

### 2.1. Persistent Volume

- PV가 released 상태에서는 사용 불가(제거 후 생성). available 상태일 때 사용 가능
- 실제 PV 데이터 저장위치
  - hostPath : 파드가 떠있는 노드에 저장 (해당 노드 로컬 디스크), 상용/프로덕션에 비적합
  - nfs : 스토리지 서버

### 2.2. Lifecycle

1. Provisioning : 볼륨으로 사용할 물리적 공간 확보하고 볼륨을 생성
2. Binding : PV와 PVC 연결. **PV와 PVC는 반드시 1:1 매핑**
3. Reclaiming : 사용이 끝난 PVC를 삭제하고, 사용중이던 PV를 다시 사용할 수 있는 상태로 반환하고 초기화. retain과 delete 정책이 있으며, recycle은 deprecated.
   - retain : 수동으로 PVC 삭제시 **PV 계속 존재(released). PV 삭제해도 데이터는 지워지지 않음**. 관리자가 직접 정리 필요
   - delete : 수동으로 PVC 삭제시 **PV와 데이터 자동 삭제**

### 2.3. Provisioning Type

#### 2.3.1 Static Provisioning

- PV/PVC 직접 만들어야 함

#### 2.3.2 Dynamic Provisioning

- PVC만 직접 만들고, PV는 직접만들지 않음

- PVC 생성 -> **StorageClass가 PV 자동으로 생성 (Not PVC)**

- Provisionier(StorageClass) 설치 필요

- Pod가 스케줄링 될 때 PV 생성

- 데이터 저장위치는 StorageClass 확인 필요

  - hostPath :  /opt/local-path-provisioner

  - nfs-provisioner : 공유폴더 아래에 데이터 저장. PVC 삭제 시 PV 자동 삭제되지만, 공유폴더에 백업폴더(archived) 자동생성

    ``````bash
    # storage class
    $ kubectl get sc
    $ kubectl describe sc nfs-client # archivedOnDelete=true 

- ReclaimPolicy : 기본 delete -> retain 변경가능

## 3. Deployment

- 어플리케이션 배포를 책임지는 쿠버네티스 리소스

- 배포 정책 : Rolling (default), Recreate (일괄 업데이트)

- 레플리카셋이 있을 경우 롤백 가능 (레플리카셋 삭제 시 롤백 불가)

  ```bash
  $ kubectl rollout status deployment nginx
  $ kubectl rollout history deployment nginx
  $ kubectl rollout undo deployment nginx # 가장 최신버전으로 롤백
  
  # 오래전 특정 버전으로 롤백하려면 annotation에서 이미지 버전 확인
  $ kubectl describe replicaset <rs-name>
  $ kubectl rollout undo deployment nginx --to-revision=2
  ```
